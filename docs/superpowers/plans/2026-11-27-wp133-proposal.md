# WP-133 — proposed contract-law implementation

Status: approved by owner on 2026-11-27: “approved. proceed.”
Baseline: merged WP-132, `origin/main` at `d076e56` (2026-11-27).

## Outcome and boundaries

Implement catalog M4 through the existing module framework: consumer withdrawal,
warranty, continuing-contract termination, subscription traps/unwanted marketing
and passenger compensation. Keep `vertragsrecht` experimental with draft/proposed
review metadata under D-071. Preserve the owner's uncommitted AGENTS.md edit.
No frontend, deployment, publication, live inference or actual corpus population.

Deliver the nine roadmap subpackages: dated primary-source verification,
versioned parameters, deterministic deadlines/calculators, guarded drafts,
public intake schema, dossier, DE/EN/de-LS copy, at least 15 synthetic goldset
cases, offline reports and compliance notices. Human review remains deferred;
offline checks do not establish live pipeline quality or promotion readiness.

## Specific architectural extension proposed for approval

Extend the existing corpus boundary with `egbgb` and `eu261` source types in the
catalog, module source mapping and PostgreSQL constraint, using the single
Alembic chain with a guarded downgrade. Enable EGBGB through the existing
Gesetze-im-Internet adapter. Add an official EUR-Lex adapter for Regulation
(EC) 261/2004 through the existing scrape/chunk dispatch, preserving article
identities, official URLs, version hashes and source dates. Reuse existing
HTTP timeout, bounded retry and source-pacing controls. Add article citation
recognition only where the current retrieval/citation contracts require it.
No new service, dependency, database or automatic module selection.

Why: the current module maps only BGB; the scraper supports federal statutes
and existing special sources, but has no EUR-Lex dispatch. M4 explicitly requires
EGBGB information duties and the EU passenger-rights regulation. Treating EU
articles as BGB paragraphs would misstate provenance and legal identity.

## Module implementation within existing extension points

- Use existing qualified event/knowledge/receipt deadlines for supported
  withdrawal, warranty, evidentiary-presumption and limitation paths. Keep
  different legal effects separate: a presumption period is not a filing
  deadline. Verify anchors, outer limits, rollover and exceptional regimes
  before encoding them. Prefer module calculators for composite dates rather
  than expanding the shared deadline engine; unsupported cases return explicit
  missing-input/review results.
- Pure, parameter-backed default-interest calculation with dated base-rate
  segments, qualified withdrawal-end calculation and flight-compensation
  distance bands. Exact money arithmetic; explicit applicability and reduction
  facts. A distance band alone must not establish entitlement. Do not infer
  distance, default, extraordinary circumstances or adequate withdrawal notice.
- Guarded withdrawal, defect-notice/cure-period, termination and passenger-claim
  drafts. Keep unconfirmed material as `[BITTE PRÜFEN]`; no automatic sending.
- Intake/dossier/static copy identify exceptions, missing facts and referral
  needs. Update disclaimer addenda/version and prompt pins deliberately;
  maintain module changelog and source coverage. Record implementation status
  in the existing roadmap/decision conventions without recreating deleted
  root release ledgers.

## Alternatives and consequences

Recommended: the additive corpus extension above and otherwise existing module
interfaces. This requires a migration, parser/provenance regressions and source
documentation, while maintaining legal-area ownership in the module.

Alternative: module-only implementation with static EGBGB/EU references and no
new ingestion. This avoids shared changes but leaves roadmap source coverage
incomplete and passenger retrieval unsupported. A separate EU ingestion service
adds infrastructure without a demonstrated need and is not recommended.

Any further material shared extension discovered during source verification
requires a specific proposal before implementation; this proposal does not
authorize an open-ended deadline/citation redesign.
